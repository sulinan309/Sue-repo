对应《攀岩知识库｜框架与建设思路 v0.1》第 11、12、13 章。

---

## 01｜首期验收对照

《知识库框架》12 章列了 8 条验收标准。当前状态：

| 验收标准 | 状态 | 说明 |
| --- | --- | --- |
| 能从任意首批技巧追溯到物理原理、标准 Beta 和来源 | **部分达成** | 物理原理和来源已连通并由脚本校验；标准 Beta 待岩馆视频接入 |
| 能从一种常见卡点找到多个候选解释，不强行给出唯一原因 | **达成** | 16 个卡点，每个 ≥2 个候选解释，`validate.py` 强制 |
| 能从一段视频生成可确认事实、一个局部提示和一项现实任务 | **结构就绪** | 链路已通（见 `query.py --chain`），需要真实视频验证 |
| 同一单元可生成科普内容、模型检索内容和产品任务 | **达成** | 每个技巧含科普脚本素材；`build.py` 产出检索 JSON；任务单元独立 |
| 每条关键建议都有适用条件、安全边界、审核人与版本 | **部分达成** | 字段齐全且强制校验；审核人待签署 |
| 可以记录「建议无效」和「证据不足」 | **部分达成** | 证据等级含「证据不足」；案例单元模板已定义，待真实数据 |
| 专家能持续修改内容，无需修改底层结构 | **达成** | Markdown + front matter，普通编辑器可改 |
| 新增力量、心理、安全知识时可沿用同一体系 | **达成** | 同一模板与证据体系，`tools/` 无需改动 |

三条「部分达成」全部卡在同一件事上：**需要真实岩馆的标准 Beta 视频和用户视频**。
这不是知识库能自己解决的，它是项目三（MVP 核心环节轻验证）的输入。

## 02｜当前规模

《知识库框架》11.1 建议的首期规模，与实际产出对照：

| 建议 | 实际 | 差异说明 |
| --- | --- | --- |
| 1 套术语和单元模板 | 1 套 | `docs/00-知识库规范.md` + `kb/glossary.yaml` |
| 5 个底层动作原则 | 5 | — |
| 8 个首批物理原理 | 8 | — |
| 10 个核心技巧主题 | 10 | — |
| 每项技巧 ≥3 个标准 Beta 片段 | **0** | 需要合作岩馆视频，未开始 |
| 每项技巧 ≥1 条科普脚本、1 个提示、1 项任务 | 达成 | 提示共 30 条，任务 18 个 |
| 20—30 个专家审核案例 | **0** | 需要用户视频和专家审核，未开始 |
| 1 套证据等级、审核和版本规则 | 1 套 | 由 `validate.py` 强制执行 |

框架文档没有单列卡点单元，实际建了 **16 个**。
原因：轴二（问题→行动）需要一个自然语言入口，
用户说的是「我脚老是滑」而不是「我的法向力不足」。
卡点单元承担这个入口，也是「多个候选解释」这条验收标准的载体。

## 03｜未完成的部分

### 需要外部输入才能推进

| 缺口 | 依赖 | 归属项目 |
| --- | --- | --- |
| 标准 Beta 片段（`beta_refs` 全空） | 合作岩馆的标准 Beta 视频 | 项目三 |
| 真实案例（`cases` 全空） | 用户未完攀视频 + 专家审核 | 项目三 |
| 三类审核签署（`review.status` 全为 pending） | 攀岩专家、物理审核人、教学审核人 | 项目一收尾 |

**审核未签署的直接后果**：`dist/kb.approved.json` 当前为空，
按《知识库规范》06 节，产品的自动输出没有可用内容。
内容本身已经就绪，卡在审核流程，不卡在写作。

### 已知的表达边界

以下内容**故意没有写**，因为首期没有依据：

- 身体条件（身高、臂展、柔韧性）与 Beta 选择的对应关系——需要真实案例数据；
- 「某方法对某类用户更有效」——《知识库框架》8.2 列了这种关系，但首期无数据支撑；
- 掉落原因的单一归因——证据等级体系里属于「专家假设」，不进产品自动输出；
- 心理层面的干预建议——`FAULT-HESITATE-013` 明确把动作承诺问题划给心理库，技巧库不越界。

## 04｜需要先做的决定

《知识库框架》13 章列了 10 个待决问题。其中 4 个已在本次建设中做了默认选择，
**这些是可以推翻的默认值，不是最终决定**：

| 问题 | 本次采用的默认值 | 理由 |
| --- | --- | --- |
| 知识库用表格、文档数据库还是定制后台 | **Markdown + YAML front matter，git 管版本** | 专家用普通编辑器就能改；脚本可校验可编译；需要时能直接映射成数据库表 |
| 中文术语以岩馆用语还是教练体系为主 | **国内岩馆日常说法为主**，教练体系说法进 aliases | 面向城市大众玩家，用他们已经在说的词 |
| 首批十个技巧是否调整 | **保持框架文档的十个不变** | 覆盖了新手最高频的卡点，且物理原理清楚 |
| 每项技巧覆盖多少墙面角度和难度 | **在 `applies_to` / `not_applicable` 里逐条写明** | 比统一规定覆盖数量更实用；折膝的「板墙上无效」这类信息只能逐条写 |

仍然需要人来定的 6 个：

1. **谁担任技巧库主编和最终审核人**——直接卡住 `review.status`，最优先；
2. **物理内容由谁审核**——8 个物理单元需要具备相关学科背景的人签署；
3. **标准 Beta 的导入、切片和标注由谁完成**——决定 `beta_refs` 什么时候能填上；
4. **哪些知识公开用于科普，哪些只进专家模型**——目前全部按可公开处理；
5. **用户视频怎样进入案例库并关联下一次结果**——影响案例单元的字段设计；
6. **内容验证和技术轻验证怎样共同反馈知识库优先级**——决定下一批扩展哪些主题。

## 05｜下一步

按依赖顺序：

### 立刻可以做（不依赖外部）

1. **三类审核**。57 个单元全部是 `pending`。审核通过后 `dist/kb.approved.json`
   才有内容，产品才有可用知识。这是当前唯一的硬阻塞。
2. **物理表述复核**。8 个物理单元的公式和简化假设需要学科背景的人过一遍，
   特别是摩擦（板墙上「贴墙更容易滑」这条反直觉结论）和冲量（死点的解释）。

### 依赖岩馆接入

3. **导入标准 Beta，填 `beta_refs`**。每项技巧至少 3 个片段。
   这一步完成后，验收标准第一条才能从「部分达成」变成「达成」。
4. **建立案例单元**。收集用户未完攀视频，记录专家建议和下一次结果，
   包括**无效案例**——《知识库框架》12 章明确要求能记录「建议无效」，
   只积累成功案例会让知识库失去纠错能力。

### 依赖前两条

5. **为项目二（恐龙 IP）输出选题**。10 个技巧单元的「科普脚本素材」小节
   已经按「钩子 + 类比 + 结论」写好，可以直接作为脚本起点。
   建议首发从反直觉的三条开始：板墙贴墙更容易滑、髋贴墙让手省力、死点练的是时机不是高度。
6. **为项目三（轻验证）提供检索**。`tools/query.py` 已经是可用的检索原型，
   接入真实视频时替换输入端即可。

## 06｜维护约定

- 每次提交前跑 `python3 tools/validate.py`，它检查结构完整性不检查文风；
- 改动结论、安全边界或提示 → 升主版本，`review.status` 退回 `pending`，重走三类审核；
- 增加情境、案例、Beta 引用 → 升次版本；
- 措辞、错字、补链接 → 升修订号；
- 修改原因写在 commit message 里，不另建修改记录表；
- **知识库贯穿四个项目持续建设，不在项目一结束后冻结。**
