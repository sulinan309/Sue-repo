# 攀岩知识库｜规范 v0.1

本文件定义知识库的**结构约定**。专家修改内容时不需要改动结构；结构变更需要单独提出并升版本。

对应《攀岩知识库｜框架与建设思路 v0.1》第 07、08、09 章。

---

## 01｜存储形式

每个知识单元 = 一个 Markdown 文件。

```
文件头（YAML front matter）  →  结构化字段，供工具校验、编译和检索
文件体（Markdown）          →  给人看的解释、脚本素材、教学语言
```

选这种形式的原因：

- 专家用普通编辑器就能改，不需要后台；
- 结构化字段可以被脚本校验和编译成模型可检索的 JSON；
- 版本、审核记录和修改原因由 git 天然承载；
- 需要升级为数据库时，front matter 可以直接映射成表。

首期不建图数据库。关系用 ID 引用表达，由 `tools/validate.py` 保证引用不断裂。

---

## 02｜编号规则

编号一经发布不可更改，也不可复用。内容作废时标 `status: deprecated`，不删除编号。

| 前缀 | 含义 | 格式 | 示例 |
| --- | --- | --- | --- |
| `PRIN` | 底层动作原则 | `PRIN-{原则}-{序号}` | `PRIN-CONTACT-001` |
| `PHY` | 物理原理 | `PHY-{原理}-{序号}` | `PHY-FRICTION-004` |
| `TEC` | 技巧 | `TEC-{层}-{技巧}-{序号}` | `TEC-MOV-FLAG-001` |
| `FAULT` | 常见卡点 | `FAULT-{现象}-{序号}` | `FAULT-BARNDOOR-016` |
| `TASK` | 现实任务 | `TASK-{任务}-{序号}` | `TASK-SILENT-FEET-001` |
| `BETA` | 标准 Beta 片段 | `BETA-{岩馆}-{线路}-{序号}` | `BETA-XM01-R117-003` |
| `CASE` | 真实案例 | `CASE-{年月}-{序号}` | `CASE-2609-014` |

技巧层（`TEC` 中的 `{层}`）取自技巧库六层：

| 缩写 | 层 |
| --- | --- |
| `PER` | 感知与决策 |
| `POS` | 身体位置 |
| `MOV` | 具体技巧 |
| `CON` | 手脚组件 |
| `STR` | 动作策略 |

底层动作原则不进 `TEC`，单独用 `PRIN`。

## 03｜技巧知识单元模板

字段对应框架文档 7.2。`必填` 的字段缺失会导致 `validate.py` 失败。

```yaml
---
id: TEC-MOV-FLAG-001            # 必填，唯一
type: technique                 # 必填
name: 旗式                       # 必填，中文主名称
aliases: [flagging, 挂旗, 外旗]   # 必填，可为空数组；用于术语归一
layer: 具体技巧                   # 必填，六层之一
status: active                  # active | draft | deprecated

one_liner: >                    # 必填，一句话定义：这个技巧做了什么
  用一条不承重的腿改变身体的质量分布或蹬墙方向，抵消开门力矩。

solves:                         # 必填，解决哪类动作问题
  - 两点支撑同侧时身体向外旋转
prerequisites: []               # 前置能力，技巧 ID 数组

applies_to:                     # 必填，适用情境
  wall_angle: [slab, vertical, overhang]   # slab | vertical | overhang | roof
  hold_types: [sidepull, crimp, jug]
  move_direction: [lateral, up]
  grade_range: "V0-V6"
not_applicable:                 # 必填，哪些情况效果有限或风险较高
  - 双脚都必须承重的高张力仰角段

principles: [PRIN-STABLE-002]   # 必填，关联底层动作原则
physics: [PHY-TORQUE-003]       # 必填，关联物理原理

phases:                         # 必填，单次动作三阶段
  prepare: 判断开门方向...
  execute: 送出旗腿...
  stabilize: 稳定后再释放手...

observables:                    # 必填，从普通单机位视频能看见什么
  - 非承重腿是否越过身体中线
faults: [FAULT-BARNDOOR-016]    # 关联卡点
hints:                          # 必填，最少剧透的一句话建议
  - 试试把左脚送到身体右后方。
tasks: [TASK-FLAG-SWITCH-007]   # 关联现实任务

safety:                         # 必填，安全边界
  - 旗腿蹬墙时不要蹬在落区正上方的岩点上

beta_refs: []                   # 标准 Beta 片段 ID；首期为空
cases: []                       # 真实案例 ID；首期为空

sources:                        # 必填，知识来源
  - type: research
    ref: "Biomechanical Principles and Techniques—A Systematization for Sport Climbing"
    url: https://pmc.ncbi.nlm.nih.gov/articles/PMC13027491/
evidence_level: 专家共识         # 必填，见 05 节

review:                         # 必填
  status: pending               # pending | fact_checked | climb_reviewed | approved
  fact: null                    # 事实审核人
  climb: null                   # 攀岩审核人
  teaching: null                # 教学审核人
  version: 0.1.0
  updated: 2026-08-25
---
```

文件体固定四节，供不同下游取用：

```markdown
## 物理原理
（为什么这样做有效。给攀岩专家模型和恐龙 IP 共用。）

## 动作要点
（用户应该关注什么。产品提示和科普脚本从这里取。）

## 常见问题
（容易在哪里失效。对应 faults 字段的展开。）

## 科普脚本素材
（恐龙 IP 用。一个钩子 + 一个可视化类比 + 一句可执行结论。）
```

## 04｜其余单元模板

### 物理原理单元（`type: physics`）

对应框架文档 7.3。

必填：`id` `type` `name` `aliases` `one_liner` `strict_definition` `plain_explanation`
`model_assumptions` `key_variables` `climbing_manifestation` `techniques`
`misconceptions` `sources` `evidence_level` `review`

`techniques` 是反向引用，允许为空（由 `build.py` 自动补全并交叉校验）。

### 动作原则单元（`type: principle`）

必填：`id` `type` `name` `one_liner` `meaning` `physics` `observables` `techniques`
`sources` `evidence_level` `review`

### 卡点单元（`type: fault`）

卡点是「问题 → 行动」轴的入口，也是产品里用户最先能描述的东西。

必填：`id` `type` `name` `aliases` `user_language`（用户会怎么说）
`observables`（视频里看得见什么）`candidate_explanations`（多个候选原因，各带证据要求）
`techniques`（可选解法）`hints` `tasks` `safety` `evidence_level` `review`

**`candidate_explanations` 必须是数组且长度 ≥ 2。** 单一原因的卡点单元不予通过——
框架文档 12 章要求「能从一种常见卡点找到多个候选解释，不强行给出唯一原因」。

### 现实任务单元（`type: task`）

必填：`id` `type` `name` `goal` `technique_refs` `steps` `evidence`（完成证据）
`fallback`（做不到时降级成什么）`safety` `grade_range` `review`

`evidence` 必须是产品能从视频或用户确认里拿到的东西。「感觉更稳了」不是证据。

## 05｜证据等级

对应框架文档 9.2。内容账号、专家模型和产品反馈共用同一套标记。

| 等级 | 含义 | 表达强度 |
| --- | --- | --- |
| `可确认事实` | 来自视频、线路或用户确认 | 可以直接陈述 |
| `研究证据` | 有同行评议来源支持 | 可以陈述，注明适用范围 |
| `专家共识` | 教学体系或多位专家一致 | 「通常」「一般来说」 |
| `专家假设` | 对原因或限制因素的候选解释 | 「可能是」「一种解释是」，必须给替代解释 |
| `证据不足` | 明确停止推断 | 「我看不准」，退回标准 Beta 或人工确认 |

规则：

1. **一个知识单元只标一个 `evidence_level`，取该单元内最弱的一条主张。**
   混合等级的内容拆成两个单元。
2. 标 `研究证据` 必须在 `sources` 里给出可访问链接。
3. 标 `专家假设` 的内容**不进入产品自动输出**，只进专家审核队列和内容素材
   （对应 MVP 文档 8.5「专家假设：首版不自动输出」）。
4. 物理原理里的公式用于解释关系，**不用于生成人体上的精确数值**。

## 06｜三类审核

对应框架文档 10.2。三类审核可以由不同人完成，缺一不可。

| 审核 | 检查什么 | 通过标记 |
| --- | --- | --- |
| **事实审核** | 来源、术语、物理表述是否准确 | `review.fact` |
| **攀岩审核** | 建议在真实线路里是否合理、是否可操作 | `review.climb` |
| **教学审核** | 普通用户能否理解并安全尝试 | `review.teaching` |

`review.status` 取值流转：

```
pending → fact_checked → climb_reviewed → approved
```

- 涉及物理解释的技巧，`review.fact` 需要具备相关学科背景的人签署；
- 涉及疼痛、损伤或心理干预的内容，走对应专业审核流程，不由攀岩教练单独通过；
- **只有 `approved` 的单元可以进入产品自动输出。** `build.py` 会分别导出
  `dist/kb.json`（全量，供检索和内容生产）和 `dist/kb.approved.json`（供产品调用）。

## 07｜版本

`review.version` 用语义化版本：

| 变更 | 升哪一位 | 例 |
| --- | --- | --- |
| 结论变了、安全边界变了、提示改了 | 主版本 | 0.1.0 → 1.0.0 |
| 增加情境、案例、Beta 引用 | 次版本 | 0.1.0 → 0.2.0 |
| 措辞、错字、来源补链接 | 修订号 | 0.1.0 → 0.1.1 |

修改原因写在 git commit message 里，不另建修改记录表。

**结论变更（主版本）必须重新走一遍三类审核**，`review.status` 退回 `pending`。

## 08｜关系类型

框架文档 8.2 列了 15 种关系。首期在 front matter 里用字段名承载，不建独立关系表：

| 关系 | 承载字段 |
| --- | --- |
| 属于 | `layer` / `type` |
| 依赖 | `prerequisites` |
| 适用于 | `applies_to` |
| 不建议用于 | `not_applicable` |
| 解决 | `solves` / `faults` |
| 由某原理解释 | `physics` / `principles` |
| 视频中表现为 | `observables` |
| 通过某任务练习 | `tasks` |
| 由某 Beta 展示 | `beta_refs` |
| 受某安全条件约束 | `safety` |
| 已在某案例中验证 | `cases` |

尚未承载、需要时再加字段的关系：**容易混淆、可以替代、可以组合、对某类用户更可能有效**。
前三种目前放在 `aliases` 和文件体里；第四种要等真实案例数据，首期没有依据。

## 09｜工具

```bash
python3 tools/validate.py     # 校验必填字段、ID 唯一性、引用完整性、证据等级用法
python3 tools/build.py        # 编译 dist/kb.json 和 dist/kb.approved.json
python3 tools/query.py <关键词|ID>   # 按卡点、技巧或情境检索，模拟专家模型的调用
```

依赖：Python 3.8+、PyYAML。

`validate.py` 应当在每次提交前跑通。它检查的不是文风，是**结构完整性**：
引用的 ID 是否存在、必填字段是否齐全、卡点是否至少给了两个候选解释、
标 `研究证据` 的单元是否给了链接。
