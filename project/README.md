# 项目协作机制

五个长期工作单元 + 共享项目文件 + 定时任务。

真人攀岩专家、设计师、内容运营是**按需介入的外部资源**，不是常驻角色。

## 为什么是文件而不是对话

四个 agent 各自在独立上下文里运行，**它们之间不共享对话记忆**。
上一次某个 agent 想了什么、决定了什么，只有写进文件才留得下来。

所以这套机制的真实约束是：**没写进文件的事等于没发生。**
每个 agent 的定义里都有一条「每次工作结束时覆盖写自己的状态文件」，
那不是形式，那是它下次醒来唯一能读到的东西。

## 谁能写哪些文件

写权限严格分开，因为并行运行时同时改一个文件会互相覆盖。

| 角色 | 独占写 | 只读 |
|---|---|---|
| 项目经理 `pm` | `project/00`–`03`、`project/日报/` | `project/status/*`、其余全部 |
| 研究专家 `research` | `climbing-kb/**`、`project/status/研究专家.md` | `annotator/`、`product/`、`qa/` |
| 产品经理 `product` | `product/**`、`project/status/产品经理.md` | `climbing-kb/`、`annotator/`、`qa/` |
| 全栈工程师 `engineer` | `annotator/**`、`project/status/工程师.md` | `climbing-kb/`、`product/`、`qa/` |
| 测试 `qa` | `qa/**`、`project/status/测试.md` | 其余全部，**尤其不改 `annotator/`** |

跨界的事一律走「状态文件里提需求 → 项目经理汇总 → 对方认领」，
不允许直接改别人的文件。

**这套权限是写在各 agent 定义里的约定，不是机制强制的。**
agent 的 `tools` 字段只能限制用哪些工具，没法限制写哪个路径。
所以它靠的是每个 agent 自己遵守，以及 pm 在日报里核对。
真出现越界，靠 git diff 能看出来。

**机制本身的变更**——新增角色、调整权限、修改交接契约——由主会话做，
不由 pm 做。pm 负责在既定机制内运转（排任务、盯依赖、记决策、写日报）。

## 工作链路与交接契约

每个箭头都是一次交接。**交接有完成标准，不是把文件扔过去就算数。**

```
研究专家 ──①──▶ 产品经理 ──②──▶ 全栈工程师 ──③──▶ 测试 ──④──▶ 真实用户
    ▲                                            ▲        │           │
    │                                            └─ 缺陷 ─┘           │
    └────────────────────────⑤──────────────────────────────────────┘
```

测试卡在工程与用户之间：**没过测试的东西不出门。**
缺陷不由测试自己修，退回工程师——写代码的人不该是唯一判断它对不对的人。

**① 研究专家 → 产品经理**
- 交付：知识单元（标明证据等级与审核状态）、可观察量清单、评测集
- 完成标准：产品经理能据此回答「用户看到什么判断、这个判断有多准、在什么情况下不准」
- 硬门槛：`专家假设` 等级的内容不能进产品自动输出；只有 `approved` 能自动输出

**② 产品经理 → 全栈工程师**
- 交付：PRD、用户流程、验收标准、指标定义
- 完成标准：工程师能据此估出工作量，并且**每条验收标准都能写成一个测试**
- 硬门槛：验收标准里的每个数字都要指到评测集或线上指标

**③ 全栈工程师 → 测试**
- 交付：可运行版本、变更说明（**哪个数变了、为什么**）、自测结果
- 完成标准：测试能一条命令跑起来并复现工程师报告的数字
- 硬门槛：声称「重构不改行为」的改动要用哈希证明，不能只是声明

**④ 测试 → 真实用户**
- 交付：测试报告（含**本次没有验证什么**）、缺陷清单、回归基线更新
- 完成标准：验收标准逐条对照过；评测集三类案例分别报了通过率；
  已知限制清单是从实测得出的，不是从想象得出的
- 硬门槛：**易误判案例的通过率要单独报**，混在总通过率里等于没报

**⑤ 真实用户 → 研究专家 / 产品经理**
- 交付：真实案例（**尤其是失败的**）、指标数据、用户反馈
- 完成标准：每条反馈都能定位到一个知识单元 ID 或一条产品决策
- 这一环最容易断。断了的表现是：知识库只有成功案例，产品指标只有正向的。

**项目经理贯穿全程**：每日读三份状态文件，更新看板、风险、日报。
优先级冲突和进度偏差由他推动；**范围变更、里程碑推迟、技术路线切换这类重大决策
他不拍板**，写进日报「待决策」上交，必要时由人决定。

## 并行运行时的提交纪律

agent 在后台跑的时候，主会话不要用 `git add -A` 提交。

**已经踩过一次**：`pm` 正在写决策记录，主会话在它写完前检查了一遍
（当时还没落盘）、随即 `git add -A` 提交了自己的改动——结果 pm 刚写完的
D-003 / D-004 / R-007 被卷进了一条只写着「新增第五个角色」的提交里。
内容没丢，但**提交信息和提交内容对不上**，将来按日志回溯会找错地方。

规则：

1. agent 在跑 → 主会话只 `git add <明确路径>`，不用 `-A`
2. 或者等 agent 的完成通知到了再提交
3. 提交前用 `git status --short` 看一眼有没有不属于本次改动的文件
4. 已经卷进去了就**如实说明，不要改写历史**——分支是共享的，
   force-push 的代价比一条不精确的提交信息大

## 定时任务

每日进展日报由 Routine 定时触发（见 `project/00-项目总表.md` 的「机制」一节）。
Routine 是**持久**的，存在服务端，不随会话结束而消失。

注意：会话内的 `CronCreate` 是另一回事——它只活在当前会话里、7 天自动过期，
不适合承载长期机制，这里没有用它。

## 怎么用

```
# 让某个角色干活
> 用 research agent 把易误判案例补进评测集
> 用 pm agent 盘一下这周进度

# 或者直接描述任务，由主会话选角色
> 定义 MVP 的核心闭环
```

主会话是编排者：拆任务、派给对应 agent、收结果、必要时把决策交给人。
