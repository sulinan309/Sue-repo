## D-001 · 陈旧输出目录只告警不阻断

**严重度** 高 · **指派** 工程师 · **状态** 待修 · **复现** `qa/用例/t03_陈旧目录告警.py`

`climbanno/anchor.py::check_fresh()` 发现 `summary.json` 缺
`pose_reliable_rate` / `analyzable_windows` 时，往 stderr print 一行就返回。
**返回值是 `None`，不抛异常，不改退出码。**

### 复现

```bash
$ python3 -c "
import sys; sys.path.insert(0,'annotator')
from climbanno import anchor
print('返回值 =', repr(anchor.check_fresh('annotator/out6')))"
[警告] annotator/out6/summary.json 缺少 pose_reliable_rate、analyzable_windows——这是旧版管线的输出，数字与当前管线不一致。请重跑 annotate.py。
返回值 = None
```

### 为什么是高

1. 调用方**在程序里拿不到任何信号**：不能 `if stale: ...`，也 catch 不到。
2. 告警只走 stderr。`2>/dev/null`、日志只收 stdout、notebook 里跑，都会把它吞掉。
   `t03` 单独测了这一点：`check_fresh` 在 stdout 上一个字都没有。
3. 最要命的下游是 `make_case.py --update-measured` —— 它经
   `anchor_measures → anchor.load → check_fresh` 进来，喊完之后**照常把旧版
   管线的数字就地写进 `climbing-kb/kb/cases/*.md` 的 `measured` 块**。
   这正是 `annotator/README` 记的那次事故：`out5` 换 `out6`，
   `+2.0s` 从 −0.50 变 −0.38，最小间距从 0.37 变 0.26，全程无报错。

### 该不该改成硬失败——测试的判断

**该。** 建议：

- `check_fresh()` 返回缺失字段列表（空列表 = 新鲜），让调用方能判断；
- `anchor.load()` 默认在陈旧目录上 `raise SystemExit`，
  加 `--allow-stale` / `allow_stale=True` 作为唯一逃生口，
  且逃生时在**产物里**留痕（写进 `summary` 或案例的 `versions`），
  而不是只在终端上说一句。

理由不是「严格更好」，是**这条防线保护的下游是知识库**。
渲染一张卡片错了，重跑就是；写进 `kb/cases/*.md` 的数字会被后续所有分析引用，
而且看不出它是哪一版跑的（另见 D-008）。
喊一声但照常放行，等于把「要不要相信这个数」的责任推给了当时有没有人在看终端。

**不建议**在 `compare.py` / `card.py` 里也硬失败——那两个是探索性工具，
中断的代价大于收益。分界线是：**会写进知识库的路径硬失败，只出图的路径告警。**

## D-002 · `summary.json` 缺失时完全沉默

**严重度** 中 · **指派** 工程师 · **状态** 待修 · **复现** `qa/用例/t03_陈旧目录告警.py`

```python
def check_fresh(outdir):
    p = pathlib.Path(outdir) / "summary.json"
    if not p.exists():
        return          # ← 一个字都不说
```

一个只有 `keypoints.npz` + `evidence.jsonl` 的残缺目录（写盘中断、
手工拼凑、复制漏文件）能一路走到出数，且没有任何提示。

### 复现

`t03` 的用例「summary.json 整个缺失：目前完全沉默」：
从 fixture 复制一份、删掉 `summary.json`，`check_fresh` 的 stderr 为空字符串。

### 建议

「文件不存在」应当和「字段缺失」同级告警——两者都是「这个目录不可信」。
连 `summary.json` 都没有，比字段旧更严重。

## D-003 · 「T0 起 2.0 秒内高度变化」差一帧

**严重度** 中 · **指派** 工程师（定口径）+ 研究专家（改正文）· **状态** 待修
**复现** `qa/用例/t04_案例口径一致性.py`

同一句话里的同一个量，两个窗口：

| 出处 | 取法 | out7 | out5 |
|---|---|---|---|
| `measured.相对承重脚高度变化["+2.0s"]` | `rise(idx(s, 2.0))` = 第 **T0+60** 帧点采样 | **+0.99** | −0.50 |
| 案例正文 / `facts` / `annotator/README` card 一节 | 60 帧窗口 `range(60)` 的末帧 = **T0+59** | **+0.97** | −0.51 |

`CASE-2608-002` 的 `measured` 写 `+2.0s: 0.99`，同一份文件的 `facts` 写
「T0 起 2.0 秒内相对承重脚高度变化 **+0.97** 倍躯干长」，正文对照表也写 +0.97。
`CASE-2608-001` 上两种取法都四舍五入到 −0.50，所以看不出来——
**两个配对案例对同一句话用了不同口径，而其中一个恰好掩盖了它。**

顺带：`measured.横向偏移.帧数 = 60`，取的是 `dx[t0:t0+60]`（T0..T0+59），
和同一个 `measured` 块里 `+2.0s` 的 T0+60 又不是同一个窗口。

### 复现

```bash
$ python3 -c "
import sys; sys.path.insert(0,'annotator'); sys.path.insert(0,'qa/用例')
import qalib as Q
from climbanno import anchor
s = Q.load_nv('qa/fixtures/out7')
print('T0+60 点采样 = %.4f' % anchor.rise(s, anchor.idx(s, 2.0)))
print('T0+59 窗口末 = %.4f' % anchor.rise(s, s['t0'] + 59))"
T0+60 点采样 = 0.9942
T0+59 窗口末 = 0.9688
```

### 建议

先定一个口径（建议统一到 60 帧窗口，与 `横向偏移.帧数` 一致，
且「2.0 秒内」按字面就该是 60 帧而不是 61 帧），
再由 `make_case.py --update-measured` 重算，正文跟着改。
不要两边各改各的——那只会多出第三个数。

## D-004 · `summary.source` 不记录 `--range` 偏移

**严重度** 高（当前潜伏）· **指派** 工程师 · **状态** 待修
**复现** `qa/用例/t01_固化输入完整性.py`

`annotate.py` 的 `--range 起:止` 直接把 `frames_bgr` 切片，
后面所有索引从**切片后的第 0 帧**起算。但 `summary["source"]` 只写了
`video`（完整路径）和 `frames`（切片后的帧数），**没有写起点**。

`anchor.load(outdir, video)` 会**从头**重读完整视频，然后拿 `frames[i]` 去配
`xy[i]`。起点为 0 时凑巧对齐；起点非 0 时画面和数字整体错位，且不报错。

### 现状证据

`out5` 的原视频有 **299 帧**，`keypoints.npz` 只有 **258 行**——
说明跑的是 `--range :8.6`（起点 0，所以侥幸对齐）。
换成 `--range 2:10` 再跑一次，`compare.py` 画出的每一帧都会错 60 帧，
上屏数字照常显示。

```bash
$ python3 -c "
import cv2, json
s = json.load(open('qa/fixtures/out5/summary.json'))
cap = cv2.VideoCapture(s['source']['video'])
n = 0
while cap.read()[0]: n += 1
print('视频实际帧数 =', n, ' summary.source.frames =', s['source']['frames'])"
视频实际帧数 = 299  summary.source.frames = 258
```

### 建议

`summary["source"]` 加 `range` / `start_frame`，`anchor.load()` 读到之后
对帧索引做同样的偏移。一行字段，堵住的是一整类无声错位。

## D-005 · `Drive.knee_reliable` 恒为 `True`

**严重度** 中 · **指派** 工程师 · **状态** 待修 · **复现** `qa/用例/t05_关节可信度与拒答.py`

`climbanno/drive.py:232-237`：

```python
# 缩短不等于「没发生发力」——只等于「膝角这个量不可信」。
# 所以不丢弃事件，只标记，让下游压制依赖膝角的结论。
knee_ok = float(np.mean(bad[side][i:j + 1])) <= 0.4
if not knee_ok:
    i += 1        # 投影伪影：不生成事件，也不占用去重间隔
    continue
```

注释说「不丢弃事件，只标记」，紧接着的两行就把事件丢了。
`Drive` 的构造点（`drive.py:326`）在这个 `continue` 之后，
传进去的 `knee_ok` 必然是 `True`。于是：

- `drive.py:102` `if not self.knee_reliable: pass` —— 不可达
- `drive.py:345 / 349` 的「（该机位膝角不可测）」文案 —— 不可达
- `coach.py:117` `if not d.knee_reliable:` —— 不可达

### 复现

`t05` 在 out5 / out7 上、用三种 `reliable` 掩膜跑 `drive.detect()`，
共取到 **12 个发力事件，全部 `knee_reliable=True`**。

### 建议

两条路选一条，别留着现在这种「注释说 A、代码做 B、字段留着不用」的状态：

- **要标记**：去掉 `continue`，让事件带着 `knee_reliable=False` 出来，
  由 `candidates()` 和 `coach.py` 压制依赖膝角的那几条结论
  （现有的分支已经写好了，只是进不去）；
- **要丢弃**：删掉 `knee_reliable` 字段和三处不可达分支，把注释改成事实。

倾向前者：膝角不可信不等于没发力，`detect_rises()` 那条不依赖膝角的路径
正是为这种情况准备的，事件本身不该消失。

## D-006 · `wall_H` 未落盘

**严重度** 高 · **指派** 工程师 · **状态** 待修 · **复现** `qa/用例/t05_关节可信度与拒答.py`

`holds.detect_stable()` 产出的逐帧单应 `Hs`（墙面坐标系）只活在
`annotate.py` 的内存里。`keypoints.npz` / `evidence.jsonl` /
`holds.json` / `summary.json` 一个都没存它。

管线跑 `drive.detect` / `detect_stalls` / `detect_rises` 时都传了 `wall_H=Hs`。
所以**这三个检测器的管线口径，只要原视频没了就永远无法复现**。

### 影响有多大

`t05` 在 out5 上量了同一段停滞：

| 停滞段 | 管线（墙面坐标） | 图像坐标 | 差 |
|---|---|---|---|
| 2.2–6.07s | **−0.03** | **−0.24** | 0.21 |
| 6.37–8.6s | −0.49 | −0.46 | 0.03 |

第一行的 **−0.03** 就是 `CASE-2608-001` 的头条数字
（「接下来的 3.9 秒净上升 −0.03：脚在上面，人没上去」）。
少了墙面补偿，它变成 −0.24——同一个结论换了一个量级。
`annotator/README` 早写过这条教训（「发力位移必须在墙面坐标里算」，
实测相机漂移 183px），现在的问题不是算错，是**算对了但存不下来**。

### 建议

把 `wall_H` 写进 `keypoints.npz`：258 帧 × 3×3 float64 ≈ 18KB，
`None` 的帧用 NaN 填。代价极小，换来的是整个 `drive.*` 层可以纳入回归。
在那之前，`qa/fixtures/` 对这一层是**结构性覆盖不到**的，
不是测试没写。

## D-007 · `review.py` 在「结尾即最高点」的素材上崩溃

**严重度** 高 · **指派** 工程师 · **状态** 待修 · **复现** `qa/用例/t06_基线对比拦截.py`

### 复现

```bash
$ cd annotator && python3 review.py ../qa/fixtures/out7/evidence.jsonl
...
  File "/home/user/Sue-repo/annotator/review.py", line 134, in <dictcomp>
    "双肘同时弯曲": round(float(np.nanmean(both_bent[sl])) * 100),
ValueError: cannot convert float NaN to integer
$ echo $?
1
```

### 根因

`review.py::posture()`：

```python
peak = int(np.nanargmin(hip[:, 1]))       # 髋部图像 y 最小 = 最高点
segs = {"上攀": slice(0, peak + 1), "下攀": slice(peak + 1, n)}
```

`peak == n - 1` 时「下攀」段长度为 0 → `np.nanmean(空)` 得 `NaN`
→ `round(float(nan))` 抛 `ValueError`。

out7 正是这种素材：`peak = 94`，`n = 95`。

### 为什么是高

**每一段成功的尝试都长这样。** 剪到动作完成为止的片段，
结尾就是全片最高点。也就是说 `review.py` 在最该分析的那类素材上直接不可用，
而且是硬崩溃 —— 好在它崩了，没有静默给出错数字。

顺带：崩之前 stderr 已经有两条 `RuntimeWarning: Mean of empty slice`，
那是同一个根因的早期信号。

### 建议

空段返回 `None` 而不是参与 `round`，并在输出里明写「本片没有下攀段」。
分段本身是对的，不该为了不崩把分段去掉。

## D-008 · 「知识库有多少条 observables」有三个数

**严重度** 低 · **指派** 工程师 · **状态** 待修 · **复现** `qa/用例/t08_知识库口径.py`

| 出处 | observables 总数 | 单元数 |
|---|---|---|
| `annotator/README.md:522` | **122** | — |
| `qa/fixtures/out5,out7 · summary.json` | **127** | 57 |
| 当前 `climbing-kb/dist/kb.json`（2026-08-28 17:20） | **168** | 70 |

（最后一行是活的：本轮工作期间它从 156/66 涨到 168/70。
这恰恰说明问题——前两个数是死的快照，却没有任何地方标明它们是快照。）

根因是良性的（知识库在管线跑完之后长大了），但表现是这个项目最忌讳的形状：
**同一个量在三个地方是三个数，而且没有任何地方说明它们是不同时刻的快照。**

更实际的一半：产物只记了「当时有多少条」，**没记知识库的版本或提交号**。
事后无法判断某份 `summary.json` 是对着哪一版知识库跑的——
`emitted_observables` 里那 8 条当时是否真的存在，也就无从复核。

### 建议

1. `annotator/README` 里的静态数字改成「见 `summary.json` 的 `knowledge_base.kb`」，
   或者由脚本生成；
2. `kb_link.capability_report()` 往 `kb` 块里加一个版本标识
   （`dist/kb.json` 的 SHA-256 前 12 位就够）。

## D-009 · `dist/kb.json` 会静默过期

**严重度** 低 · **指派** 研究专家 · **状态** 待修 · **复现** `qa/用例/t08_知识库口径.py`

`climbanno/kb_link.py` 读的是 **`climbing-kb/dist/kb.json`**，不是 `kb/*.md`。
`dist/` 由 `tools/build.py` 生成，而**没有任何机制强制在改完 `kb/` 之后重新 build**——
`tools/validate.py` 校验的是 `kb/`，跑通了也不代表 `dist/` 是新的。

### 实际发生过（本轮工作期间）

2026-08-28 17:08 左右，`kb/` 已有 70 个单元（研究专家新增了
`CASE-2608-003` / `FAULT-SWAP-DROP-021` / `TASK-FOOT-TAP-021` / `TEC-CON-SWAP-003`），
而 `dist/kb.json` 仍是 66 个。此刻跑 `annotate.py`，
`summary.json` 的能力对照会对着旧知识库出，而且不会报错。
17:20 再看时 `dist/` 已被重新 build，两边回到一致——**它自己好了，
所以更值得记：没有人会知道中间那段时间的产物是对着旧知识库跑的。**

### 现状

`t08` 的用例「dist/kb.json 是管线真正读的那份，不能过期」已经把它做成硬断言：
单元集合不同、或者交集里任何单元的 `hints` / `observables` 不同，直接失败。

### 建议

`tools/validate.py` 顺带比一次 `dist/` 与 `kb/`，不一致就报错并提示跑 `build.py`；
或者把 build 并进 validate。一处改动，去掉一整类「对着旧知识库出结论」。
