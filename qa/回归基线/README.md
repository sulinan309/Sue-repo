# 回归基线

> 四个 JSON 快照。**唯一输入是 `qa/fixtures/`，不依赖任何视频。**

| 文件 | 谁生成 | 内容 | 变化意味着 |
|---|---|---|---|
| `fixtures.sha256.json` | `t01` | 8 个 fixture 文件的 SHA-256 与字节数 | 输入被改了 |
| `anchor_golden.json` | `t02` | 逐帧序列哈希 + 上屏数字 + 配对论断 | `anchor.py` 的数值行为变了 |
| `reliability_golden.json` | `t05` | 四个关节的可信率、两条腿的投影压缩率 | 可信度判据变了 |
| `review_golden.json` | `t06` | `review.py` 端到端输出的哈希与条数 | 候选发现的判定变了 |

## 两层保护，缺一不可

**逐帧哈希**：`dx` / `dy` / `torso` / `ax` / `ay` 五条序列四舍五入到小数点后
6 位再取 SHA-256。采样点对得上而中间某几帧变了，抽样是抓不到的。
「重构不改行为」这句话必须由哈希来说。

**上屏数字**：T0、踩实时横向偏、`+0.4/0.5/0.8/1.0/1.5/2.0s` 的高度变化、
两条轨迹最小间距。这些是 `compare.py` 和 `card.py` 真的印在成品上的数，
哈希变了但这些没变，说明改动没落到用户看见的东西上——两者要分开报。

另外 `t02` 里还硬编码了一份 `EXPECT`（工程师报告的已知正确值），
与本目录的 JSON **互为独立来源**：基线文件被误 `--bless` 覆盖时，`EXPECT` 仍然会响。

## 基线自己也要被测

一条永远通过的基线和没有基线是一回事。`t02` 有一个灵敏度自检：
把 T0 之后的重心整体上移 **3 像素**（躯干长 186px 的 1.6%），
确认 `dy` 哈希和 `+2.0s` 上屏数字都跟着变。
反向也测：整幅画面平移 7px（模拟镜头位移）时数字**必须不变**——
承重踝作参考点本来就该抵消镜头平移，这条性质同样要钉住。

对照量级：out5 与 out6（旧版管线）的关键点最大差 98px、COM 最大差 15px，
结论从 −0.50 变成 −0.38。3px 远小于那次事故。

## 怎么更新

```bash
./qa/用例/run.sh --bless          # 重建全部
./qa/用例/run.sh t02 --bless      # 只重建 anchor 快照
```

`--bless` **不是「让测试变绿」的按钮**。基线变化必须由改动者说明
**哪个数变了、为什么**，写在提交信息里。测试不负责解释，只负责发现。
